# 人工发码与 GitHub 更新方案

状态：设计记录与独立交互预览，运行插件尚未实现激活界面、发码工具或 Kodi 更新仓库，未发布或部署。2026-10-06。

## 当前需求

- 维护者人工生成并发放授权码，授权期限为三个月。
- 用户无需注册账号、手机号或验证码。
- 发布和分发只使用 GitHub，不另设授权服务器。
- 用户从首页导航的“设置 → 版本与更新”查看版本、检查新版并发起版本更新；“版本与更新”是设置菜单中的独立入口，放在“系统信息”之后。GitHub 是发布和下载来源。
- 保留 `skin.yoplayer.infuse` 与 `plugin.video.yoplayer.home` 两个运行 ID。

## 推荐流程

GitHub 提供静态文件分发，不承担动态激活、首次设备绑定或授权计时。

1. 客户端生成随机安装标识，显示为带校验的设备码。用户将设备码提供给维护者；不采用 MAC 地址作为唯一身份。
2. 维护者在本机发码工具中填写设备码与起始日期，生成随机授权码，并用本机私钥签署对应的授权记录。
3. 仅将签名后的记录发布到 GitHub。授权码由维护者单独发给用户，原码、签名私钥、客户资料和维护者凭据不发布。
4. 用户在客户端输入授权码。客户端根据原码的 SHA256 摘要定位记录，验证数字签名、设备绑定和起止日期，然后保存缓存。
5. 续期、换机和停用由维护者重新签发或发布新的签名状态记录。客户端在后续联网检查时取得变化。

首次设备绑定由维护者签发时完成。客户端不能持有可写 GitHub Token，也不能用 GitHub Issues 或 Actions 充当带内置公共凭据的激活数据库。

公开仓库中的授权记录可被列举，因此仅保存必要的设备摘要和授权字段。摘要不等同于加密；即使没有原码，持有该设备访问权限的人也可能取得对应记录。短授权码主要用于查找，真实性来自数字签名，复制限制依赖设备检查。

## 三个月的计算

推荐从签发时确定的起始日期计算三个自然月，而非固定 90 天。授权记录包含不可由客户端修改的绝对起止时间，使用 UTC 存储，在界面转换为当地时间。

例如当地时间 2026-10-06 20:00 开始，2027-01-06 20:00 到期。目标月份不存在同一日期时取该月最后一天，例如 1 月 31 日开始，4 月 30 日到期。

此前讨论的“首次激活后起算”属于在线后台方案。在纯静态 GitHub 方案中，无法由可信后台记录首次激活时间。推荐改为上述签发时确定的起始日期；若仍要求可信首次激活起算、输入码后自动绑定第一台设备，需动态授权服务。这项日期起算变更仍是建议，未记作用户已确认。

## 签名与缓存

- 采用 Ed25519 等非对称数字签名。私钥只留在维护者本机，客户端包含公钥和密钥标识；实现前验证 CoreELEC Python 验签依赖与跨平台兼容性。
- 签名覆盖格式版本、授权记录 ID、授权码摘要、设备摘要、权限范围、起始时间、到期时间、修订号及状态。
- 签名载荷使用明确的字节格式，例如签署 base64url 包装的 UTF-8 JSON 原始字节，避免客户端重新序列化造成验签差异。
- 缓存建议允许正常客户端断网使用最多七天，且不能越过三个月的到期时间。七天策略是建议，尚未作为实现或接受结果。
- 停用和延期在客户端取得新记录后生效。断网时无法立即吊销；缓存和本机时钟也不构成抵抗 root 用户篡改的可信执行环境。
- 重装和换机需要人工重新绑定。重新绑定不自动增加授权期限，沿用原到期时间，除非维护者明确续期。

## 更新分工

| 位置 | 职责 |
|---|---|
| GitHub 源码与标签 | 保存与版本对应的源码 |
| GitHub Releases | 正式版本说明、两个独立安装 ZIP、SHA256 校验清单 |
| GitHub Pages 静态仓库站点 | Kodi 仓库索引、索引校验、符合 Kodi 目录规则的 ZIP 和相关资源 |
| 设置 → 版本与更新 | 用户查看当前版本、检查新版、阅读更新内容、发起安装并查看授权信息 |
| Kodi 插件管理 | 处理插件安装与依赖；原生自动更新按其设置运行 |

用户第一次安装 YoPlayer 仓库插件；后续主要从“设置 → 版本与更新”检查和发起更新，不需要自行前往 GitHub 下载每版 ZIP。原生 Kodi 插件界面仍作为管理入口。首次仓库接入需验证已有 ZIP 安装的两插件能被该仓库识别，且 Home/Skin 依赖可正常升级。

仅上传 GitHub Release 不能自动形成 Kodi 更新仓库。Kodi 默认 ZIP 地址规则需要如 `addons/<addon-id>/<addon-id>-<version>.zip` 的目录；Release 附件 URL 不能直接当作这一目录使用。首版建议将已验证 ZIP 的相同字节复制到 Pages 发布目录，并按 Kodi 规则命名。安装包复制不重新构建插件、不覆盖已交付档案。

Pages 的部署方式、站点容量、GitHub 在目标网络上的可达性和 Kodi 依赖解析需实际验证。没有备用分发源时，GitHub 网络故障会影响首次激活与更新；本地缓存用于有限容错。

默认原生 Kodi 仓库更新不承诺安装期间双插件原子切换、空闲时安装、自动回滚或自定义签名强制验证。索引或 ZIP 的 SHA256 校验与发布者数字签名是不同能力。若要求这些行为，需增加专门的管理模块并验证完整安装路径。

## 设置菜单中的版本与更新入口

用户在 2026-10-06 的最新设计反馈中将入口改为“首页导航的设置 → 版本与更新”。现有首页设置按钮通过 `infuse.py,settings` 调用 `infuse_home_menu.py` 的设置菜单，菜单已有“首页布局、系统信息、系统工具、高级设置”四项。计划在“系统信息”之后新增独立的“版本与更新”，说明文字为“检查更新、升级与授权”。

现有“系统信息”继续调用 `open_native('1182')`，对应 `source/skin.yoplayer.infuse/1080p/custom_1182_HomeSystem.xml`；其中已有“版本与设备详情”入口，指向 `custom_1183_SystemDetails.xml`。打开“设置”先显示包含全部条目的设置菜单，选择其中的“版本与更新”才进入更新页；更新页返回键回到设置菜单。预览默认从首页开始，不恢复上次停留的更新子页面。正式实现时再选择并核对更新页的窗口编号，当前仅修改独立预览和本设计记录。

`infuse_system.py` 已通过 `xbmcaddon.Addon(...).getAddonInfo('version')` 读取 Skin/Home 实际安装版本，适合作为版本数据接入点。高级设置里的原生 `SettingsSystemInfo.xml` 及其 `native-versions` 按钮属于另一条现有入口，继续保留。

新增的“版本与更新”页沿用已有字体、主题和遥控焦点规则。当前版本、检查结果与操作集中展示，授权状态、三个月期限、到期日期、设备码和授权码输入放在同页的“授权信息”区域。宽屏并排展示版本更新与授权信息，窄屏依次排列。

| 内容 | 行为 |
|---|---|
| YoPlayer 当前版本 | 显示本机实际安装的 Skin 版本与 Home 版本，不把源码候选版本当作已安装版本 |
| Kodi / CoreELEC 版本 | 保留现有系统版本、构建与设备信息；本入口更新范围为 YoPlayer 两插件 |
| 最新稳定版 | 检查成功后显示对应的 Skin/Home 配套版本；以数字版本段比较，不按字符串排序 |
| 检查更新 | 用户主动触发；显示检查中状态并避免重复请求 |
| 更新内容 | 展示该版本的用户可读说明，以及必要的兼容性要求 |
| 更新版本 | 仅在有兼容新版、下载源就绪且当前无播放时提供安装操作；安装前重查播放状态 |
| 上次成功检查 | 显示实际检查时间；旧结果标明为缓存，网络错误不覆盖成“已是最新版” |

页面无需打开即持续轮询 GitHub。进入页面读取本机版本和已有检查结果，点击“检查更新”才刷新远端版本。请求有明确超时；返回键可退出检查或下载，不能中断已经开始的安装提交。

需覆盖的状态：尚未检查、检查中、已是最新版、发现新版、更新源尚未配置、网络请求失败、依赖不兼容、正在播放暂缓安装、下载中、安装中、安装完成与安装失败。当前候选版本高于公开最新稳定版时说明“当前版本较新”，不主动降级。

发现新版后保留用户控制，按“更新版本”再展示变更说明与“更新后将重载界面”的提示。更新成功必须重读实际安装版本并核对配套关系，不能仅凭下载完成或发出安装命令判断成功。部分安装或失败时保留真实已安装状态，提供明确的重试或恢复信息。

安装调用需基于已验证的 Kodi 原生插件管理能力实现，不假定存在任意 ZIP 的 JSON-RPC 安装接口。若必须导航到原生安装确认，应保持从“版本与更新”发起、核对结束状态并能返回该入口；不先实现一个没有安装能力的“更新成功”按钮。

授权输入、有效期和设备码放在更新页的“授权信息”区域。版本检查与授权状态分别显示，现有 GPL 功能和公开源码的权利继续按原许可保持。

## 接入与许可范围

当前检查和打包工具仅接受两个运行插件。新增仓库插件可在单独的仓库构建产物中生成；若新增独立运行模块，需要明确扩展检查、版本和打包规则，不能直接绕过现有保护。原版档案、当前包、字体、许可、真实观看历史及播放行为继续保持。

现有皮肤采用 GPL v2，Home 声明 GPL-2.0-or-later。发码不得撤销这些已分发代码的 GPL 权利；对 GPL 派生代码继续提供对应源码和许可。闭源商业模块是否独立取决于实际代码关系，不能仅靠拆文件夹判定。

本记录没有确定新增独立付费功能，也没有给现有首页、播放或 GPL 功能设置到期锁。后续实现先提供授权状态与验签流程；付费权限须对应明确、适合该许可安排的独立功能。

## 实现顺序与验证

1. 实现本机签发工具及本地台账，验证自然月边界、签名篡改、设备不匹配、过期、停用修订及续期行为；不在测试输出中泄露真实授权码或密钥。
2. 实现客户端输入、状态显示与缓存验证。首版不改变既有播放、续播、轨道选择或媒体同步。
3. 增加静态仓库构建入口，从已验证的交付 ZIP 生成索引、校验和与发布目录；验证 ID、最低依赖、下载路径、文件一致性及拒绝覆盖规则。
4. 运行 `python tools/check_infuse_structure.py`，运行文件有变化时升版，再使用 `python tools/package_project.py` 打包。
5. 发布 GitHub 更新仓库和新包；按当前设备协调、备份及播放守卫规则进行实际接受。Windows 只同步，CoreELEC 功能接受与实体电视/遥控/CEC 接受分别记录。

目前另有独立交互预览：设置菜单直接展示“版本与更新”，可体验版本检查、更新内容、模拟下载与安装、网络失败、播放中暂缓更新、较新本机版本，以及同页的示例授权输入。菜单按用户提供的浅色界面保留原有条目和层级。所有版本、媒体播放、授权与安装状态均为预览数据；预览不连接 Kodi、CoreELEC 或授权服务，不修改实际安装。

本轮落地设计记录与交互预览。现有 GitHub 发布、运行插件、设备和真实授权状态均未因此改变。
